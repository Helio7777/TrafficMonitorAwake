# 迈从鼠标电量查询与休眠评估

评估日期：2026-10-08。对象是本机 `TrafficMonitor-LogiBattery` 项目的
MCHOSE 后端（插件声明版本 1.1.2），不是 Awake 插件本身。本次仅审查该后端，
没有修改鼠标设置、发送实机查询或进行电流测量。

## 结论

当前实现存在增加通信耗电、干扰鼠标休眠的风险，不宜宣称“查询不影响续航”。
代码能够证明它会周期性主动发送命令，但不能证明每次命令都会唤醒无线鼠标。
接收器是否直接返回缓存、是否通过无线链路请求鼠标，以及命令是否重置鼠标的
休眠计时，取决于具体型号、接收器和固件，需要实测。

## 代码证据

| 位置 | 已确认行为 | 影响 |
| --- | --- | --- |
| `src/MchoseHid.h:43` | 成功轮询和失败重试的等待间隔都是 5 秒 | 无空闲暂停、无失败退避；实际周期还包含查询耗时 |
| `src/MchoseHid.cpp:278` | G3 A 通过 `WriteFile` 发送电量请求 | 不是单纯读取应用内缓存 |
| `src/MchoseHid.cpp:301` | E2 优先 `HidD_SetFeature`，失败后尝试输出报告 | 同样会主动发送 HID 命令 |
| `src/MchoseHid.cpp:442` | 先发命令，再最多约 1 秒等待输入报告 | 读取超时不代表鼠标未被查询唤醒 |
| `src/MchoseHid.cpp:566` | 持续循环，不判断鼠标活动状态 | 鼠标闲置期间仍持续查询 |

每个查询周期会重新枚举 HID 接口，并在一个端点失败后尝试下一个。
每个查询端点的设备句柄由 RAII 管理，函数返回后关闭，没有把查询句柄一直持有
到下一次等待；这不能消除重复主动通信造成的风险。

Microsoft 明确说明 [`HidD_SetFeature`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidsdi/nf-hidsdi-hidd_setfeature)
会发送 feature report。USB 空闲电源管理也可能受 I/O 活动影响，见
[选择性挂起说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/selective-suspend-in-a-kmdf-function-driver)。
USB 接收器的挂起与无线鼠标自身的休眠是两个不同层次，不能直接等同。

Awake 仅提交系统/显示器电源请求，没有查询鼠标或模拟鼠标输入。它可能让电脑
保持运行，从而使另一个插件继续轮询；这与直接强制鼠标不休眠不同。参见
[`PowerSetRequest`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-powersetrequest)。

## 建议的省电策略

- 使用期间降低主动查询频率，例如每 60 秒一次；该间隔是工程建议，不是厂商保证。
- 根据目标鼠标的实际输入识别空闲，空闲后停止主动查询；其他鼠标或键盘活动
  不应被误认为该鼠标仍活跃。没有可靠活动检测时，提供手动刷新模式。
- 失败后逐步退避，例如 60、120、300 秒；避免设备休眠时持续快速重试。
- 保留最近有效电量及读取时间，明确标注缓存/过期，避免把缓存显示成实时数据。
- 给手动刷新加限速。单纯改成每分钟查询仍可能周期性唤醒鼠标，不能保证休眠。

## 实机验证方法

记录鼠标型号、固件和厂商配置的休眠时间；关闭厂商驱动/网页等其他查询程序。
让电脑在两组测试中都保持运行，分别停用和启用电量插件，鼠标静置时间应超过
设置的休眠时间。厂商 G3 A 页面提供休眠设置，见 [MCHOSE HUB](https://www.mchose.com.cn/gmouse/)。

分别比较恢复移动时的唤醒表现，并记录 USB 命令时序。如果条件允许，测量鼠标
电池侧静置电流，或在相同条件下进行较长时间、多次重复的续航对照。
USB 抓包只能证明接收器收到命令；唤醒延迟、短时间电量百分比变化和
`powercfg /requests` 都不能单独证明鼠标是否进入低功耗状态。
